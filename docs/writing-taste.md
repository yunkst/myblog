# 博客内容品味规范

写新文章 / 改旧文章之前读一遍。这份文档沉淀的是作者（yunkst）裁定过的内容标准，
和 `writing-a-post.md`（怎么写）互补——那篇讲机制，这篇讲取舍。

## 1. 叙事定位：像写报告

- 讲清楚两件事就够了：**功能是什么样的、它是怎么实现的**。
- 不渲染技术多难、方案多聪明；不用形容词证明价值，用场景和数字。
- 不情绪化、不喊口号、不浮夸。标题尤其要克制（被否掉的例子：「看小说看到意难平」式标题）。

## 2. 名词纪律

- **除非该幕就是讲原理，否则不要在功能介绍或其他非原理场景堆砌技术名词。**
  「Casdoor 做单点登录、Apisix + openid-connect 做统一鉴权……」这类句子对读者没有信息量，只有名词。
- 例外：p-* 原理幕可以出现技术名词，因为它是该节主题本身。
- 品牌名 / 组件名同样适用：能写「决策链记录」就不写「Langfuse 记录的决策链」，
  除非该节就在讲这个组件。

## 3. 事实纪律（最重要）

- **只写实现了的能力。** 功能与行为描述以源码为准；博客写过的每一条机制，必须能在代码里指出来。
  （教训：分级执行幕写了不存在的「测试服预演 / 管理员审批」，被读者抓出后不得不回头补实现。）
- 设计与实现要分清：未实现的标成「规划 / 下一步」，不和既有能力混写。
- 数字与公开口径对齐（如媒体报导的口径），不自造数字。
- 两张图、图与文之间不能自相矛盾（教训：总览图画「绕回网关」、链路图画「直连」，两处必须同源同口径）。

## 4. 结构纪律

- **单一叙事脊**：一篇一个主线，场景之间是追问关系，不是并列陈列。
- 描述性、顺序性的叙述（「下面是我的设计方案……」）属于平铺长文，不属于地图分支场景；
  场景化写作的每一幕应该回答一个具体问题。
- **文动一致**：动画演示的必须是文字说的那件事；文字改了，动画和图同步改。
- 入口幕固定四件事：解决了什么问题、技术栈一句话、开源地址、下载 / 体验位置。

## 5. 语言风格

- 直白、简单、短句。能一句说完不写三句。
- 第一人称实事求是：做了什么、没做什么、边界在哪，都直说（「解决不了什么」这类幕要保留）。
- 虚构例子可以用，但要典型、贴近真实业务场景，读者能代入。

## 发布前检查清单

- [ ] 每个机制描述都能在源码里指出对应实现
- [ ] 非原理幕无技术名词堆砌
- [ ] 动画 / 架构图与正文口径一致，且通过 ArchDiagram 守卫测试
- [ ] 标题与正文无浮夸、无情绪化表达
- [ ] 数字与公开口径一致
