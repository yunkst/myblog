《怎么让AI安全的担负起运维工作》中提到，我把服务器完全云原生化，本节介绍如何我的开发流程

本地开发完成之后，把代码推送到 gitlab 的 dev 分支，经过 ci/cd 完成以下工作：

* 静态检查
* 打包
* 单元测试
* ai code-review ( 可以提供源码)
* gitops 触发器，更新 gitops dev 分支

argocd 发现 gitops 仓库 dev 分支发生更新，自动部署到 测试环境

线上体验没问题之后 （需要注意测试环境的数据库每日同步生产，可以参考《怎么让AI安全的担负起运维工作》中关于数据同步部分），提交 mr（pr吗？） 合并到应用主分支， gitops 触发器更新 gitops main 分支，正式修改生产环境的 镜像 tag ，部署上线。


结合 数字分身 的未来构思：

# 基础设施： 一个可以读所有代码仓库的 agent 服务，通过  rbac 约束角色可以看的代码库，对外提供以下功能：
1. 功能查询
2. 需求确定
3. 开发计划产生

功能查询是收到请求，查询对应的代码库，得出结论后返回

需求确定，收到用户的请求后，结合代码库返回问题直到所有问题都得到解答，类似 grill me 这个 skill ,用来明确方案需求
然后产出一份准确的需求文档

需求文档被用户确定之后，可以用需求文档生产开发计划

也就是 spec 到 plan 的步骤

一个 gitlab 触发器可以触发对应代码库的 ci/cd 过程， 拿到 spec 和 plan ，开始开发并根据开发规范 完成 静态检查/打包/单元测试 ，确认没有问题之后，提交到 dev 分支。 如果是后台服务，会自动完成部署到 测试服。

整个流程不需要开发人员参与，正式上线前可能需要检查下，如果有问题把 dev 分支回滚下也没什么损失， spec 和 plan 也可以复用。

随着AI 能力提升，设置好合适的工作流，我认为是可以解决绝大部分需求开发工作的
