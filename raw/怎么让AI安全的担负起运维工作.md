# 怎么让 AI 安全地担负起运维工作

运维是一个复杂、需要大量实践和知识积累的工作。

在 AI 时代，与其让我自己成为一个合格的运维人员，我认为搭建一套体系让 AI 安全地进行运维，更符合未来的大方向。人负责搭体系、定边界、做审批，AI 负责观察、判断、执行——这套东西搭好之后，日常运维的绝大部分工作 AI 都能接走，而且比人更勤快、更稳定。

问题清单：

* 体系搭建步骤
* AI 的安全边界怎么画
* 节约成本

这篇文章是这个体系跑了大半年之后的复盘：哪些设想落地了，哪些设想和生产现实撞了之后改了方向，以及 AI 在这套笼子里真实的表现。

# 安全模型：AI 的权限边界怎么画

让 AI 干运维，大家第一反应是"它搞坏了怎么办"。我的答案是：别指望 AI 不犯错，而是设计一个**犯错不可持续、密钥不可见、操作可审计**的体系。安全边界不是靠提示词里写"请你小心"，而是靠架构本身。

## 笼子：所有写操作必须经过 Git

这套体系里，AI（以及人）对集群没有直接的写权限。规则明文写在仓库的 CLAUDE.md 里：

* **禁止**：`kubectl apply / delete / edit / patch / scale` —— 任何绕过 Git 的操作都会造成"集群真实状态"和"Git 声明状态"的漂移
* **允许**：`get / describe / logs / top / port-forward` —— 读操作几乎不设限，AI 需要充分观察才能做出正确判断

写操作只有一条路：改 YAML、提 commit，ArgoCD 自动同步。这样每个变更天然具备三件事：**审计**（git log 一目了然）、**回滚**（git revert 即回滚方案）、**评审**（AI 提 MR、人合并，危险变更在合并前被拦下）。

还有一层兜底：ArgoCD 开了 `selfHeal`，就算有人绕过规则手动改了集群，下次同步会自动纠回 Git 声明的状态。**漂移不可持续，笼子会自己修。**

连例外都是论证过的：`rollout restart` 被特别放行，理由写在注释里——"重启不改变资源定义，ArgoCD 下次同步时 spec 未变不会覆盖，不会导致 GitOps 漂移"。AI 每次动手前还有四问自检：

> 这个变更能表达为 commit 吗？我是不是没耐心等 ArgoCD 自己收敛？我是在修症状，还是修 Git 里的根因？这次手动改动会被下次同步回滚吗？

## 密钥：AI 设计管道，人灌水

运维场景里最敏感的是明文密钥。这套体系里，AI 从头到尾看不到密钥的值：

```
人      在 Infisical 网页上填密钥值（明文只存在这一处）
Git     只有 InfisicalSecret CR —— "哪个 K8s Secret 来自 Infisical 哪条路径"的元数据
集群    secrets-operator 用 K8s native auth（SA TokenReview，无静态凭证）
        自动把值同步成 K8s Secret，业务照常挂载，业务方无感知
```

AI 的角色是搭"接线"：写 InfisicalSecret CR、建 reader ServiceAccount、在 K8s Auth 白名单里登记 namespace。这些全是元数据，不含任何秘密。值由人在网页上填。职责切分很清楚：**AI 设计管道，人负责灌水。**

切换过程也有验证兜底：从 SealedSecret 迁移到 Infisical 时，用脚本对两边 Secret 做 SHA256 逐键比对，不一致就禁止切换。

## 输出也要脱敏

输入要管，输出同样要管。巡检 agent 把任何内容交给 LLM、或推送到企业微信之前，先过一遍正则强制脱敏：token、password、cookie、手机号、身份证、邮箱，全部替换成 `[REDACTED:*]`。日志和告警里经常混着用户数据，而 AI 的报告会被一群人看到——不能赌它不漏。

## 经验要喂回给 AI

AI 会重复犯同样的错，但同样的坑不该踩第二次。办法是把踩过的坑沉淀成仓库里的 skill 文件：目前编码了密钥管理的 5 个已知陷阱（K8s Auth 白名单遗漏、dockerconfigjson 编码、operator ETag 缓存、空值密钥被拒、双 owner 冲突），AI 每次接触密钥相关工作都会先读它，直接绕开。

这套安全模型的实际效果：AI 可以放手干大部分日常运维——部署、排障、巡检、容量建议——而它**做不了**的事（直接改集群、看到明文、泄漏数据），是架构上不可能，而不是提示词上不允许。

# 体系搭建：清单与真实落地

下面是我当初的搭建清单，以及每一条在生产里的真实形态。清单和现实的差距，比清单本身更有价值。

## 1. 租一个集群

云服务商的托管集群（我用的是腾讯云 TKE）就行，没必要自建控制面。这个环节没有什么花巧，唯一要想清楚的是节点怎么买——放在后面的成本章节讲。

## 2. GitLab + ArgoCD：先把笼子立起来

在外部搭一个 GitLab 放代码和配置，然后在集群上部署 ArgoCD。这两步是整个体系的地基：**之后所有组件的部署，都通过"往 GitLab 提交 YAML、ArgoCD 自动同步"来完成，包括 ArgoCD 自己的升级。**

部署模式用的是 App of Apps：一个 root Application 监听仓库里 `apps/` 目录，目录下每个 `xxx-app.yaml` 就是一个 ArgoCD Application 声明。要接入新组件，只需要提交一个新的 Application YAML，root App 会自动发现并部署它。仓库里再也没有"手动执行过什么命令"的暗账。

## 3. APISIX：统一入口

网关选了 APISIX，规则简单粗暴：**所有服务必须经 APISIX 暴露，禁止 LoadBalancer 和 NodePort。**

这条规则的价值在后面才显现：因为所有流量都过同一个网关，访问日志天然集中在一处，证书统一由 cert-manager 管理——后面讲到的巡检 agent 之所以能用一份日志查出所有业务的 5xx 和攻击扫描，前提就是入口收敛。

## 4. Casdoor：内部服务的统一登录

SSO 用 Casdoor，GitLab、Grafana、Infisical 的登录都指向它。组件不多的早期看不出价值，但每多接一个服务，"不用再管一套账号"的收益就复利一次。

## 5. Infisical：密钥的归宿

密钥管理是这套体系里演进最剧烈的部分，经历了三代：

1. **明文 Secret 直接提交**——早期图快，Git 仓库里全是 `password: 123456`，做安全审计时是 P0 级问题
2. **SealedSecret**——明文在本地用 kubeseal 加密成密文提交，集群内控制器解密。Git 里没有明文了，但密钥散落在 20 多个 YAML 文件里，查一个密钥靠 grep，轮换要走"本地明文 → 加密 → 提交"全流程，且没有任何使用审计
3. **自托管 Infisical（现行）**——密钥值只存在 Infisical（网页管理），Git 里只有 InfisicalSecret CR 元数据，operator 自动同步成 K8s Secret

选 Infisical 而不是 Vault 的原因：体量小（20+ 密钥）用不起 Vault 的运维成本，Infisical 有 Web UI、原生 K8s operator、Casdoor OIDC 直连，社区版自托管免云费用。SealedSecret 保留作为应急通道——SSO 或 Infisical 挂了的时候，还有一条不依赖它们的路。

## 6. 自循环：GitLab 搬进集群

这是清单里描述最模糊、落地最顺畅的一条。原设想是"集群内搭 GitLab，把 GitOps 指向集群内的仓库，变成自循环"，实际形态：

* GitLab 通过 ArgoCD 部署在集群内（用本地 chart 模式，Helm chart 直接放在 GitOps 仓库里，因为集群访问上游 Helm 源不稳定）
* GitOps 仓库本身就托管在这个 GitLab 上
* GitLab 配置了 push webhook 通知 ArgoCD——commit 一推送，ArgoCD 秒级感知，不用等轮询

于是形成闭环：**改配置 → 提交到集群里的 GitLab → webhook 触发 ArgoCD → 同步到集群**。整套体系监控着自己、部署着自己，外部没有任何部署依赖。

## 7. 日志和报警：AI 运维的感官

这套组件是巡检 agent 的基础设施：

* **kube-prometheus-stack**（Prometheus + Grafana + AlertManager）——指标和告警
* **Loki + Promtail**——日志聚合，30 天保留
* **blackbox-exporter**——黑盒探测，从集群外看服务是否真的可用
* **企微 webhook 适配器**——AlertManager 告警和巡检报告的统一投递通道

告警规则不求全，先覆盖会直接炸的：Pod 重启频次、OOMKilled、5xx 率、证书到期、磁盘水位。误报多的规则宁可关掉——告警疲劳比告警缺失更危险，这条对 AI 同样成立。

## 8. dev / prod 分离：放弃分支模型

原设想是"dev application 监听 dev 分支，prod 监听 main 分支"。实际落地时放弃了这个方案，改用**单 main 分支 + Kustomize overlays 目录**：

```
apps/<app>/overlays/test/    ← 测试环境的差异配置
apps/<app>/overlays/prod/    ← 生产环境的差异配置
```

放弃分支模型的原因：**两个环境的配置大部分是相同的**。分支模型要求每次改动在两个分支之间来回 cherry-pick，改一个公共配置要合两次；而目录模型里 base 存通用配置、overlay 只存差异，公共改动落一处，环境差异（副本数、资源限制、镜像 tag）各改各的。

分支的差异并没有消失，而是挪到了业务代码仓库的 CI 层：master 分支构建出 `prod-日期` 镜像，deploy-dev 分支构建 `dev-日期` 镜像，CI 流水线构建完自动改 GitOps 仓库里对应 overlay 的镜像 tag。**业务仓库用分支，配置仓库用目录，各取所长。**

prod 的 Application 我保留了和 test 相同的 automated sync——有人会建议 prod 手动同步更安全，但我的经验是：真正的安全闸门在 MR 评审（人合并前看 diff），而不是同步环节。合并即部署，倒逼每个 diff 都值得被认真评审。

## 9. 数据分身：生产库 → 测试库的每日同步

这条的设想完全被生产验证了，而且演进过程本身就值得讲（见后面"生产验证"一节）。现行方案：

* 测试库每晚被生产数据**覆盖式重灌**（DROP + restore），语义是"影子环境"——测试工作不跨天保留，每天开局都是真实数据基线
* 数据源用**腾讯云托管数据库的每日逻辑备份**，而不是直连生产库 dump——dump 对生产有读取压力，而云数据库本来就自带备份，直接用备份文件恢复即可
* 备份文件经 COS 中转，按份数保留 3 份（不按时间保留——以后改同步频率也不会误删）
* 生产侧连接全部走只读副本 / 从节点（`secondaryPreferred`），不碰主库
* ES 和 Redis 明确排除：ES 依赖 PG 数据、走重建索引更稳；Redis 是缓存语义，跨天保留没意义

为什么同步数据？测试环境用真实的数据形态（数据量、脏数据、慢查询），测试结论才对生产有预见性——**后果可预见**，这是 AI 敢在测试环境大胆操作的前提。

# 巡检 agent：AI 运维的执行者

前面所有组件搭的是"感官"和"肌肉"，巡检 agent 是大脑——它每天早上 9 点自动跑一次，把集群前 24 小时的状态浓缩成一份企业微信报告，14 分钟预算，超时强杀。

## 架构：三阶段

```
Phase 1  并行扫描（约 5 分钟）
   四个维度子 agent 同时跑：攻击面 / 服务健康 / 资源水位 / 合规
   每个子 agent 带着自己的工具箱（日志查询、指标查询、K8s API）
   各自产出 findings JSON（含自评：覆盖率、置信度）

Phase 2  疑点深挖（按需，最多 5 次）
   主 agent 审视四维度 findings，识别值得深挖的疑点：
   - 跨维度、同 namespace、时间相近的异常组合
   - severity=critical 但 confidence=low 的发现
   - 子 agent 自报"没查到"的覆盖缺口
   对每个疑点派出独立上下文的研究子 agent 跨维度取证

Phase 3  聚合报告
   生产异常详写、正常项压成一行、全绿时只发"今日无异常"
```

几个刻意的设计：

* **维度并行、疑点串行**：Phase 1 四个维度互不等待，任何一个挂了其他照常；Phase 2 的深挖次数封顶 5 次，防止 agent 陷进调查循环烧 token
* **降级路径**：LLM 完全不可用时，退化为纯规则检查（不走 AI，直接拼阈值告警）——巡检的底线是"哪怕 AI 挂了，报告照发"
* **告警和巡检互补**：AlertManager 管"现在就炸了"的实时告警，巡检 agent 管"还没炸但不对劲"的趋势巡查——比如重启次数没到告警线但在 7 天基线上明显抬升

## 它看什么

四个维度的具体检查项（全部配置化，改 YAML 就能调整阈值）：

| 维度 | 检查内容 |
|---|---|
| 攻击面 | 5xx 计数、敏感路径扫描（`/admin` `/.env` `/wp-login` 之类）、高频来源 IP、登录失败突增 |
| 服务健康 | Pod 重启次数 vs 7 天基线、ArgoCD 应用同步状态、证书到期天数、黑盒探测成功率 |
| 资源水位 | CPU / 内存 / 磁盘超阈值、OOMKilled 迹象、接近 limits 的 Pod |
| 合规 | 无 limits 的容器、缺探针的 Deployment、缺 VPA 建议的工作负载 |

攻击面检查有个实现细节值得一提：因为所有流量都过 APISIX，访问日志全部落在 apisix namespace 下，按 host 区分业务。所以查业务流量的日志，实际是"查 apisix namespace + host 过滤"——这个映射关系配在 ns_host_mapping 里。**统一网关的架构决策，在这里变成了巡检能力的地基。**

## 它被关在什么笼子里

巡检 agent 的 RBAC 是只读的：ClusterRole 只有 `get / list / watch`，注释里写明 "observe-only，禁止 patch/delete/create"。它可以看 Pod、看日志、看证书、看 ArgoCD 状态，但物理上改不了任何东西。发现的异常报告给人，修复动作由人或（经评审的）AI 通过 Git 完成。

它的 LLM 凭据走 SealedSecret 注入，输出过 scrub 脱敏，报告发企业微信群。整条链路上，它是一个**只能看、只能报告、不能碰**的角色。

# 生产验证：三个真实的坑

体系设想得再好，也要看它在生产里怎么表现。挑三个有代表性的。

## 坑一：db-sync 的自我修正——我的设想对了一半

最初的 db-sync 用自建链路：凌晨直接连生产库 mongodump/pg_dump → 传 COS → 恢复到测试库。上线跑了一周，发现问题：

* mongodump 虽然走了从节点，但 dump 期间对生产仍有可感知的读取压力，还要操心 oplog 窗口会不会被截断
* 腾讯云托管数据库**每天本来就有全量逻辑备份**，自建 dump 纯属重复劳动

于是整个链路推翻重做：删掉 4 个自建 dump CronJob，改为直接拉腾讯云的托管备份文件 → 解包 → 恢复到测试库。链路短了一半，生产侧压力归零。

有意思的是，回头看我在项目最初写的设想——"为什么不用 dump 和 restore，因为 dump 对数据库有额外的压力，腾讯云数据库本来就自带备份，直接用备份文件恢复就行了"——**判断一开始就是对的，但实现时还是先走了 dump 的弯路**。教训是：对"省事路径"的本能依赖（mongodump 是文档里的标准做法），会盖过自己当初想清楚的判断。

## 坑二：Infisical 拒绝空值密钥——"缺 key"和"空值"是两回事

把 c2h4-test 的 SealedSecret 迁移到 Infisical 时，CLI 批量导入被一个 key 拦住了：`HUAWEI_CLIENT_SECRET` 的值是**空字符串**（华为推送的凭据，可能从未配置过），Infisical CLI 拒绝导入空值。

这看似小事，实际很微妙：

* 应用现在消费的就是这个空值，说明空值是"当前真值"
* 但迁移后如果这个 key 缺失，应用代码 `os.environ['HUAWEI_CLIENT_SECRET']` 会直接抛 KeyError——**缺 key ≠ 空值**，空值是拿到 `''`，缺 key 是崩溃
* 存占位哨兵值（比如 `EMPTY`）更不行——应用拿到非空假值，行为可能真的改变（比如真的去连华为推送）

最后走的路线是：先确认这个 key 是否还有存在的必要（找业务方确认功能是否还活着），而不是在平台层想办法兼容空值。这个案例后来沉淀进了密钥管理的 skill 文档，AI 下次迁移时会在动手前先扫一遍空值 key。

这个坑让我确认了一件事：**密钥迁移这种工作，恰恰是 AI 最需要"评审闸门"的地方**——AI 能把方案设计得很完整（SHA256 逐键比对、PR 分两步、观察 24h 再切换），但"空值到底算不算有效数据"这种业务语义判断，必须人来做。

## 坑三：ArgoCD CRD 永久 OutOfSync——AI 排障能力的天花板测试

某天发现一个 ArgoCD App 长期 OutOfSync，全是 CRD 类型的资源，diff 显示的还不是业务字段，而是 `metadata.labels: None vs {}` 这种元数据噪音。直觉的修复方向全部无效：给 CRD 加 label、改 ignoreDifferences、反复重刷，都不好使。

最后是 AI 读着 ArgoCD 的**上游源码**把根因挖出来的，链路大概是：

1. App 处于多步同步路径（ServerSideApply + PruneLast），operation 卡在"等待所有资源 Healthy"
2. 只要 operation 不结束，`autoSync` 直接被跳过（源码里 `app.Operation != nil` 的第一关检查）；手动触发也会撞"另一个 operation 进行中"
3. 而卡住的 operation 钉死的是**启动时的旧 revision**——后续的 Git 提交根本不在它的同步范围里
4. 更糟的是默认 controller 没配同步超时，一个不健康的资源能让整个 operation 无限挂起

解法分三层：立即解锁（终止卡死的 operation）、治本（修好那个真正不健康的资源）、兜底（给 controller 配 `--sync-timeout`）。文档里还专门写了"不要做的"：不要用 ignoreDifferences 消红字——它能消掉 ArgoCD 里的报错，但卡死的 operation 不会解锁，下次任何变更都会再次撞上，而且掩盖了真实的漂移。

这个案例的价值在于它展示了 AI 排障的正确姿势：**不满足于"重试好了"，而是追到上游源码行号级别，把"症状消失"和"根因修复"分开**。当然，能看到这一点的另一个前提是——整个过程 AI 只有读权限，所以它从一开始就没有"先 patch 一下试试"这个选项，被逼着往根因走。

# 节约成本

这套体系跑在一套"稳定性分级"的策略上。核心认知：**服务的稳定性需求越高，投入越多，但边际效益递减**——从 99% 到 99.9% 的成本，可能是从 99.9% 到 99.99% 的十分之一。所以与其全部拉高，不如分级：

## 节点策略：包年保底 + 竞价冲量

* 腾讯云竞价实例价格约为包年包月的 **1/8**，缺点是可能被回收
* 租 2 个包年包月节点，通过亲和性把关键服务钉在上面——APISIX、ArgoCD（它的 etcd）这类"挂了整个体系瘫痪"的组件
* 其余服务（测试环境、内部后台、可中断的批处理）全部落竞价节点
* 极端情况：竞价节点同时被回收，关键链路仍然存活，损失的只是测试和后台服务

## 优先级腾挪：资源不够时谁让路

用 PriorityClass 表达三级水位：

```
生产对外服务    >    内部后台    >    测试
```

* 生产服务配 HPA（副本 ≥2 的 Deployment 强制配），资源紧张时优先扩
* 内部后台（巡检、监控、CI）低于生产、高于测试，资源严重不足时驱逐测试负载
* 测试环境单副本起步——反正每晚会被数据分身覆盖，挂了损失有限

一个配套规范：每个 Deployment 必须配 VPA（建议模式，只出建议不自动改），跑一段时间后 VPA 的建议值就是资源申请的定价新闻——**用免费的数据回答"这个服务到底需要多少资源"，避免拍脑袋超配**。

## 容量按需求的 2 倍买，成本是包年的 1/3

"资源容量是需求的 2 倍，成本是包年包月的 1/3"——这两个数能同时成立，靠的就是上面的组合：2 倍容量里，只有 1/4 左右（2 个包年节点）按正价付费，其余全是竞价价格。容量冗余换的是竞价回收时的缓冲空间。

## 再往上，稳定性怎么加

如果真要追求更高稳定性，路径大致是（成本从低到高）：

1. **把"组件单点"消掉**：这是最便宜的一档。 Infisical 的 PG、ArgoCD、GitLab 这些单副本组件切多副本 + 外部数据库。大部分"集群挂了"的事故其实是"集群里某个单点组件挂了"
2. **备份的异地化**：备份文件（COS 里的数据库备份、Git 仓库本身）同步一份到跨区域/跨云的对象存储。注意 GitOps 体系有个天然优势——**整个集群的声明状态就是那个 Git 仓库**，仓库在，集群就能重建。备份异地化保护的是"仓库 + 数据库备份"这两样最不可再生资产
3. **多集群热备**：第二个集群跑同样的 GitOps bootstrap（App of Apps 模式下，新集群就是换个 destination 重新 apply 一次 bootstrap），数据靠备份恢复。RTO 是小时级，RPO 是备份间隔——对多数非金融业务够用
4. **多云 / 异地双活**：流量级双活要解决跨云网络、数据同步、全局流量调度三个问题，复杂度和成本陡增。除非业务对 RTO/RPO 的要求到了分钟级，否则不建议一步到位——从 3 到 4 的路上，先把 2 和 3 做扎实，性价比高得多

我的实际选择是停在 2：单集群 + 关键组件消除单点 + 备份异地化。原因很直白——这套体系服务的是可以容忍小时级重建的业务，为用不到的稳定性付月费不值。分级不是偷懒，是把钱花在业务真实需要的可用性档位上。

# 后记

回看这套体系跑下来的感受：

* **GitOps 是给 AI 的运维工作提供的最大基础设施**。它不只是部署方式，是把"审计、回滚、评审"三件事变成架构默认值的笼子
* **AI 的判断需要真实生产来校准**。db-sync 那个坑里，正确的判断我早就写下来了，但执行时还是走了弯路——体系和设想之间的差距，只有跑了才知道
* **安全边界的本质是职责切分**：AI 观察和提案，人审批和灌密钥，架构保证 AI 做不到越界的事。不是信任问题，是能力边界问题

下一步想把巡检 agent 从"报告异常"推进到"提议修复"——发现异常后直接生成修复 MR 挂在评审队列里，人合并即修复。笼子已经有了，剩下的只是让笼子里的手更巧。
